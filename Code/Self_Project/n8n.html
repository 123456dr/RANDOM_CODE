施工計畫書自動派送流程

課程：當機器人來上班－未來職場的 AI 必修課 期末作業｜2026

我在一家正在數位轉型的公司當行政工讀生。每份施工計畫書建立好之後，我都要下載未簽署版本存到伺服器、到官方 LINE 找到客戶傳簽署連結、一直回去看客戶簽了沒、簽完再下載一次存檔。這個專案用 n8n 把建立之後的這一整段自動化：我只要把簽署連結貼進追蹤表、勾選「開始核可」，歸檔、傳送和追蹤回簽都交給流程。

專案介紹要解決什麼問題、怎麼解決、怎麼確保不出錯、還有哪些限制。不需要技術背景。 技術介紹網路、Docker、自製網站、n8n 節點設定、建置步驟、除錯。照著做就能重現。

專案介紹 · 02

要解決的問題：一位客戶要切換四個地方

想像你是便利商店店員，每來一個包裹，你要：拍照存檔、打電話通知收件人、每隔一陣子打開記事本看對方來拿了沒、拿走後再拍一張存檔。一天十個包裹還好，五十個就一定會漏。

我的工作就是這樣，只是包裹換成「施工計畫書」，電話換成「官方 LINE」。每一步都不難，難的是要在很多地方之間切換，而且要對準同一位客戶。

手動處理一位客戶的步驟：

  1. 建立計畫書在公司系統照行事曆填客戶資料，產生簽署連結。
  2. 歸檔＋傳送下載未簽署 PDF → 找到這位客戶的伺服器資料夾存進去 → 打開官方 LINE 找到客戶 → 貼上簽署要求文字和連結。
  3. 等待回簽每隔一段時間回到系統查看簽了沒。
  4. 完成歸檔簽了之後下載已簽署 PDF → 再找一次資料夾存進去 → 在追蹤表打勾。

自動化之後，人只剩第 1 步，再加上「貼連結、勾選開始核可」這兩個動作；第 2～4 步交給 n8n。

為什麼選這一段自動化？用顧客旅程圖分析，痛點最集中在「歸檔＋傳送」：這一步要跨三個系統（計畫書系統、伺服器、LINE）並且用人腦維持「這是同一位客戶」的對應關係。這種跨系統、重複、規則明確的工作，正是工作流程自動化（workflow automation）最適合的範圍。

為什麼不連「建立計畫書」也自動化？建立計畫書需要判斷（施工類別、注意事項、派哪位師傅），而且錯了會直接影響現場施工。這一步保留給人，是刻意的自動化邊界設計：機器做重複的搬運，人做判斷與最後確認。

錯誤成本不對稱：漏存一份檔案頂多補存；但把 A 客戶的計畫書傳給 B 客戶，是個資外洩。所以〈把關設計〉的重點放在「不要傳錯人」，而不是「跑得更快」。

專案介紹 · 03

解決方案：人做判斷，n8n 做搬運

核心想法是人做判斷，n8n 做搬運：建立計畫書和「確認可以送出」留給人，其餘跨系統的下載、存檔、傳訊息、追蹤全部交給兩條自動化流程。

流程 1「發送」：我一勾選，它就去確認連結沒貼錯人 → 下載未簽版 → 存到伺服器 → 傳訊息給客戶 → 在追蹤表寫「已發送」。

流程 2「收到回簽通知」：客戶一簽完，計畫書網站就通知 n8n → n8n 再確認一次真的簽了、追蹤表對得上 → 下載已簽版 → 存到伺服器 → 追蹤表打勾 → 跟客戶說「收到了」。

兩條流程透過追蹤表的「狀態」欄接力：流程 1 寫入「已發送」，流程 2 只處理狀態是「已發送」的客戶，處理完改成「已完成」，就算同一則通知被重送，也不會重複處理。

專案介紹 · 04

把關設計：自動化也要有人負責

自動化最可怕的不是做不到，而是很快地把錯的事做很多次。人傳錯一次會發現；流程設錯了，可能一下子傳錯十位客戶。所以我在流程裡放了幾個「關卡」，就像捷運的閘門：沒過關就不會往下走。

課程第 2 單元提到，治理要變成流程裡具體的步驟。這個流程有五個：

原則流程中的做法對應課程
人工把關我在追蹤表勾選「開始核可」，流程才會傳訊息給客戶2.5 人類監督、Human in the Loop
停機流程 1：連結裡的計畫書客戶編號和追蹤表那一列對不上，就停止並通知我。流程 2：通知對不上（沒簽、狀態不是已發送、連結不符）也停止並通知2.6 停機機制
驗證來源流程 2 的 Webhook 用 Header Auth 檢查密語，陌生人打這個網址會被 403 拒絕；收到通知後再回 API 確認2.3 安全性
紀錄追蹤表記下狀態、發送時間、回簽時間、兩份 PDF 在公司伺服器的網址；n8n 的 Executions 保留每次執行細節2.3 可歸責
最小化傳給客戶的訊息只有姓名、施工時間和連結；地址、施藥人員只在計畫書裡；API 不回傳簽名圖檔2.3 資料最小化

親手驗證停機機制

  1. 製造錯誤把 C002 林美美那一列的簽署連結，故意貼成 C001 王小明的連結。
  2. 勾選開始核可等 1 分鐘。
  3. 檢查結果林美美的頻道不應該收到任何訊息；你的通知頻道收到「⚠️ 編號不符，已停止」；追蹤表狀態仍是空的；伺服器資料夾沒有多出檔案。

這段一定要錄進影片，它證明流程「會停」，而不只是「會跑」。

為什麼不做成「一貼上連結就自動傳」？因為錯誤成本不對稱（〈要解決的問題〉）：多勾一下只花一秒，傳錯客戶是個資外洩。保留一個勾選動作，是在效率和控制之間刻意的取捨。

失敗安全（fail-safe）：每個關卡在「不確定」時都選擇不做事。查不到計畫書（404）→ HTTP 節點報錯、流程中斷，不會繼續傳訊息；編號不符 → 走停機分支。失敗時的預設行為是「停」而不是「繼續」。

還可以加強的地方：

  • n8n 的 Error Workflow：任何流程失敗時自動觸發另一條流程，把錯誤通知到我的頻道，不用自己去翻 Executions。
  • HTTP Request 的 Retry On Fail：網路偶爾斷線時自動重試 2～3 次，降低誤報。
  • 部分失敗的處理：如果歸檔成功、但傳 Discord 失敗，狀態仍是空的，下次重新勾選時會再歸檔一次（覆蓋同名檔案）並重傳，結果仍然正確。這是刻意讓「重做」安全的設計。
專案介紹 · 05

限制與未來

這個作業是「模型」，像建築師的模型屋：結構和動線都是真的，但還不能住人。要真的給公司用，需要讓客戶從自己的手機打開連結、換成真的 LINE、確認簽名的人真的是客戶本人。

目前的限制影響真實環境的做法
簽署連結是 localhost只有我這台電腦打得開，客戶手機打不開網站架在公開網址並啟用 HTTPS
Discord 代替 LINE客戶不會真的收到LINE Messaging API
通知最多重試 3 次n8n 停機太久，通知會失敗，要人按「重送」訊息佇列（message queue）保存未送達的通知，或每天跑一次補償檢查，把「已簽但未完成」的找出來補做
n8n 只在 Docker 內部網路收通知外部系統打不進來n8n 架在公開網址並啟用 HTTPS，Webhook 一定要有驗證
沒有身分驗證拿到連結的人都能簽簡訊或 LINE 驗證碼確認是本人
電腦關機就停流程跟著停放在公司伺服器或雲端主機 24 小時運作

可以延伸的方向

  • 本地 AI 檢查（Ollama）：發送前讓本地模型比對計畫書內容與行事曆是否一致（日期、施工類別），不一致就停機。用本地模型是因為資料不會離開公司電腦。
  • 數據回饋（課程 17.5）：每週自動統計平均回簽天數、哪類施工最常拖延，回頭改善流程。
  • 自動提醒：超過 48 小時未簽，自動傳一則溫和的提醒訊息。

技術介紹 · 01

網路基礎：網址、HTTP、JSON、API

整個專案其實只在做一件事：幾個程式透過網址互相傳資料。先把這一章弄懂，後面每一章都會變簡單。

網址就像地址。「台北市中正區某某路 10 號 3 樓」是要找到一戶人家；網址是要找到一台電腦上的一個程式、裡面的一個東西。

HTTP 就像寄信的規則。你寄出一封「請求」（我要看第 P0001 號計畫書），對方回你一封「回應」（好，內容在這裡），信封上還會蓋一個狀態章（200 成功、404 找不到）。

JSON 就像填好的表格。大家約好用同一種格式寫資料，程式才看得懂對方寫什麼。

API 就像店家的點餐窗口。網頁是給人看的店面，API 是專門給程式用的窗口：不用看漂亮畫面，直接拿資料。

拆解一個網址

http://協定：用什麼規則溝通
localhost主機：哪一台電腦
:8080埠號：電腦上的哪個程式
/s/P0001-e7ff77路徑：程式裡的哪個東西
  • localhost 的意思是「我自己這台電腦」。
  • 埠號（port）像大樓裡的分機號碼：同一台電腦上跑很多程式，用號碼區分。這個專案用了 8080（計畫書網站）、8090（檔案伺服器）、5678（n8n）。
  • 路徑由網站自己決定。例如計畫書網站規定 /s/編號 是簽署頁、/api/plans/編號 是給程式查的資料。

兩種最常用的請求

方法意思這個專案裡的例子
GET我要「拿」東西n8n 查計畫書資料、下載 PDF；你在瀏覽器打開任何網址也是 GET
POST我要「送」東西過去n8n 把 PDF 送到檔案伺服器、把訊息送到 Discord；客戶按「送出簽署」；計畫書網站通知 n8n「有人簽了」

讀懂 JSON

{
  "id": "P0001-e7ff77",      ← 文字（字串）要用雙引號
  "status": "signed",
  "ok": true,                 ← 布林值：true / false
  "size": 505406,             ← 數字不用引號
  "files": ["a.pdf", "b.pdf"]  ← 陣列：一串東西
}

大括號 { } 是一個物件，裡面是一對對「名稱: 值」。n8n 節點之間傳的資料全部都是這種格式。

一個 HTTP 請求完整長什麼樣

n8n 查詢計畫書時，實際送出和收到的文字大致如下：

Request（n8n → plan-site）
GET /api/plans/P0001-e7ff77 HTTP/1.1
Host: plan-site:8080
Accept: application/json
Response（plan-site → n8n）
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 412

{"id":"P0001-e7ff77","customer_id":"C001","status":"unsigned", ...}
  • Header（標頭）是信封上的資訊。最重要的是 Content-Type：告訴對方內容是 JSON（application/json）、PDF（application/pdf）還是表單。n8n 下載 PDF 時要把 Response Format 設成 File，就是因為內容不是文字。
  • localhost 其實是 127.0.0.1，一個永遠指向「自己」的特殊位址（loopback）。這就是為什麼在容器裡寫 localhost 會連到容器自己（〈Docker〉）。
  • 埠號範圍是 0～65535，同一個位址的同一個埠同時只能有一個程式在聽。8080 被佔用時 Docker 會啟動失敗，這時把 compose 裡的 "8080:8080" 左邊改成別的號碼即可。

上傳檔案用的 multipart/form-data

JSON 只能放文字，PDF 是二進位資料，所以上傳檔案改用 multipart/form-data：把一個請求切成好幾段，每段一個欄位，用一串隨機的分隔線（boundary）隔開。這也是網頁上「選擇檔案＋送出」表單的格式。

POST /api/upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----n8nBoundary

------n8nBoundary
Content-Disposition: form-data; name="folder"

C001_王小明
------n8nBoundary
Content-Disposition: form-data; name="file"; filename="C001_未簽署.pdf"
Content-Type: application/pdf

%PDF-1.4 ……（PDF 的二進位內容）……
------n8nBoundary--

網址裡的中文：百分比編碼

網址原本只允許英文字母、數字和少數符號。中文會先轉成 UTF-8 位元組，再把每個位元組寫成 %XX。例如「王」是三個位元組 E7 8E 8B，寫成 %E7%8E%8B。所以檔案伺服器回傳的網址會長這樣：

http://localhost:8090/C001_%E7%8E%8B%E5%B0%8F%E6%98%8E/C001_%E6%9C%AA%E7%B0%BD%E7%BD%B2.pdf
                      └── 王小明 ──────────────┘      └── 未簽署 ──────────────┘

瀏覽器網址列會自動顯示回中文，兩種寫法指向同一個檔案。

API 設計風格

這個專案的 API 採用 REST 的基本精神：用路徑表示「資源」（/api/plans/P0001… 是一份計畫書），用 HTTP 方法表示「動作」（GET 讀取、POST 新增或執行），回應用狀態碼表達結果。好處是任何會發 HTTP 請求的工具（n8n、curl、Python、瀏覽器）都能直接串接，不必綁定特定程式語言。

Docker：一個指令把四個程式架起來

正常要在電腦上跑 n8n，要先裝 Node.js、對好版本、裝一堆套件；計畫書網站要裝 Python 和字型。每台電腦環境不同，常常「我電腦可以、你電腦不行」。

Docker 的做法是：把程式和它需要的一切裝進一個便當盒。便當盒到哪台電腦都一樣，加熱就能吃。

Docker 名詞比喻
Image 映像檔食譜＋材料包（還沒煮）
Container 容器照食譜做出來、正在吃的便當
Dockerfile手寫食譜：自己做 image 的步驟
Volume / 掛載保鮮盒：便當吃完丟掉，保鮮盒裡的東西還在
Port mapping取餐窗口號碼：外面的人從幾號窗口拿到這個便當
Compose一張點餐單：一次點四個便當，一個指令全部上桌

容器跟虛擬機有什麼不同

虛擬機（例如 VMware 裡的 Kali）模擬一整台電腦，有自己的作業系統核心，開機要幾十秒、佔好幾 GB。容器共用主機的 Linux 核心，只是用核心功能把程式隔開：

  • namespaces：讓容器以為自己有獨立的檔案系統、網路、行程編號。
  • cgroups：限制容器能用多少 CPU 和記憶體。

Windows 沒有 Linux 核心，所以 Docker Desktop 會在背景開一個輕量的 Linux 虛擬機（WSL 2），容器跑在它裡面。

Dockerfile 逐行：計畫書網站怎麼被做出來

FROM python:3.12-slim                # 從官方精簡版 Python 開始
RUN apt-get update && apt-get install -y --no-install-recommends fonts-wqy-zenhei \
    && rm -rf /var/lib/apt/lists/*     # 裝中文字型（PDF 才能顯示中文），清掉暫存縮小體積

Image 是一層一層疊起來的（layer），每一行指令一層，Docker 會快取沒變的層。先複製 requirements.txt 再裝套件、最後才複製 app.py，是為了改程式時不用重裝套件：只有最後一層失效，重建幾秒就好。

容器之間怎麼找到對方：內建 DNS

Compose 會替同一個檔案裡的服務建立一個私人網路（名稱類似 n8n作業_default），並提供內建的 DNS：在這個網路裡，服務名稱就是主機名稱。所以 n8n 寫 http://plan-site:8080，DNS 會把 plan-site 解析成那個容器的內部 IP。

方向反過來也一樣：計畫書網站要通知 n8n 時，寫的是 http://n8n:5678/…，不是 localhost。

而瀏覽器在 Windows 上，不在 Docker 網路裡，認不得 plan-site 這個名字，只能走 port mapping 用 localhost:8080。同一個網站有兩個網址，要看「誰在連」，這是整個專案最容易搞混的地方。

depends_on 的限制：它只保證「啟動順序」，不保證對方已經準備好接收請求。流程是人勾選後才觸發，那時網站早就啟動了，所以這裡夠用；正式系統會再加 healthcheck。

關於 :latest：每次重新下載可能拿到新版本，畫面或節點名稱可能改變。正式環境會固定版本號（例如 n8nio/n8n:1.x.x），讓結果可以重現。

技術介紹 · 03

模擬計畫書網站 plan-site

這是我寫來代替公司系統的小網站。它做四件事：

  1. 讓我填客戶資料、按「製作計畫書」。
  2. 給我一個簽署連結，這個連結就是要傳給客戶的東西。
  3. 客戶打開連結，看計畫書內容，在最下面用手指或滑鼠簽名。
  4. 隨時可以下載兩種 PDF：簽名前的和簽名後（印著客戶簽名）的。

它同時有一個給程式用的窗口（API）讓 n8n 查資料、下載 PDF。而且客戶一簽完，它會主動打電話給 n8n說「P0001 簽好了」，n8n 不用一直來問。

自己先玩一次

  1. 打開 http://localhost:8080填 C001 王小明的資料，按「製作計畫書」。
  2. 複製簽署連結完成頁上的連結長得像 http://localhost:8080/s/P0001-xxxxxx。
  3. 開新分頁看 API把連結的 /s/ 改成 /api/plans/，就會看到上面那種 JSON，status 是 unsigned。
  4. 打開簽署連結簽名簽完再重新整理 API 頁，status 變成 signed。（正式測試流程時先不要簽，留給 n8n 偵測。）

技術組成

  • Flask：Python 的輕量網頁框架，用 @app.get("/路徑") 把網址對應到函式。
  • 資料儲存：每份計畫書一個 JSON 檔，存在容器的 /data，也就是電腦上的 plan_data 資料夾。量少時比資料庫簡單、打開就能看。
  • PDF：用 ReportLab 在每次請求時即時產生，不存檔。所以簽名一存進去，下一次下載就是已簽版。字型用文泉驛正黑（TTC 字型集的第 0 個字型），找不到時改用 ReportLab 內建的 CID 中文字型，避免中文變成方塊。

簽名是怎麼變成 PDF 上的圖

客戶在 <canvas> 上畫 → 送出時 canvas.toDataURL('image/png')
  → 得到 "data:image/png;base64,iVBORw0KGgo…"（圖片變成一長串文字）
  → 放進隱藏欄位，跟表單一起 POST 到 /s/編號/sign
  → 伺服器用正規表示式檢查格式，存進 JSON 的 signature_png
  → 產生 PDF 時 base64 解碼回圖片，畫在「客戶簽名」欄位

Base64 是把任意位元組轉成 64 種安全字元的編碼，讓圖片可以放進表單或 JSON 這種只吃文字的地方。代價是體積變大約三分之一。

狀態機：只能往前走

  建立 ──▶ unsigned ──(客戶簽名)──▶ signed
                                   │
            再簽一次 ───────────────┘ 直接轉回簽署頁，不覆蓋

狀態只有兩個、只能單向前進。已簽署後再 POST 簽名會被忽略，第一次簽署的紀錄不會被改掉。這讓 n8n 的判斷很單純：看到 signed 就一定是最終結果。

簽完主動通知 n8n：Webhook 發送端

客戶按下送出後，網站做三件事：存簽名 → 開一個背景執行緒去通知 n8n → 立刻把客戶轉回簽署頁。通知放在背景，是因為 n8n 慢或掛掉時，客戶不該卡在轉圈圈。

# 送出的請求
POST http://n8n:5678/webhook/plan-signed
Content-Type: application/json; charset=utf-8
X-Webhook-Secret: anxin-demo-secret-2026

{ "event": "plan.signed", "id": "P0001-e7ff77", "customer_id": "C001",
  "status": "signed", "signed_at": "2026-11-30 14:05:12", "sent_at": "…", … }
機制做法為什麼
重試失敗最多試 3 次，間隔 2、4 秒（越等越久，叫 backoff）n8n 剛好在重啟、網路短暫不通時，不會就這樣漏掉
正式／測試網址自動切換先送 /webhook/，回 404 就改送 /webhook-test/n8n 流程還沒啟用時正式網址不存在；這樣開發和上線都不用改設定
結果寫回每份計畫書的 notify 欄記下成功或失敗、送到哪個網址、試了幾次、錯誤原因可追蹤；清單頁直接顯示，失敗一眼看得到
手動重送清單上的「重送」按鈕、POST /api/plans/編號/notify3 次都失敗（例如 n8n 關機一整晚）時的補救
密語標頭每次附 X-Webhook-Secret，n8n 用 Header Auth 檢查n8n 的 Webhook 網址等於一扇對外的門，沒有密語的人敲門會被 403 拒絕

通知只說「誰簽了」，不帶簽名圖片；n8n 收到後會再回頭向 API 確認（〈把關設計〉「不信任通知內容」）。

資安設計

設計防的是什麼
編號 = 流水號 + 6 位隨機十六進位（secrets.token_hex(3)），約 1,677 萬種組合IDOR（不安全的直接物件參照）：如果連結只是 /s/2，客戶把 2 改成 3 就看到別人的計畫書
編號必須完全符合 P\d{4}-[a-z0-9]{6} 才去讀檔路徑穿越：防止有人傳 ../../etc/passwd 這種編號去讀系統檔案
API 回應移除 signature_png資料最小化：n8n 只需要知道簽了沒，不需要簽名圖檔本身
建立與簽署時用 threading.Lock競態條件：兩個請求同時進來時，流水號重複或簽名互相覆蓋
輸出到 HTML 前一律跳脫（escape）XSS：客戶名稱欄位如果被填入 <script>，不會被當成程式執行

這是模擬用的網站，沒有登入機制，知道連結的人就能簽。真實的電子簽署系統還需要身分驗證（例如簡訊驗證碼）、時間戳記與防竄改的簽章，見〈上線考量〉。

公司伺服器 file-server：本機資料夾＋伺服器網址

想像一個有兩扇門的抽屜：一扇門在你房間（檔案總管裡的 公司伺服器 資料夾），一扇門開在走廊（網址 http://localhost:8090）。不管從哪扇門放東西進去，另一扇門打開都看得到，因為裡面是同一個抽屜。

為什麼用 HTTP 上傳，而不是讓 n8n 直接寫檔

n8n 有「Read/Write Files from Disk」節點可以直接寫檔，但較新版本預設限制 n8n 只能存取特定資料夾（安全考量），還要處理容器使用者權限、資料夾不存在等問題。改成「伺服器提供上傳 API」有三個好處：

  • 職責分離：n8n 只負責流程，檔案怎麼存、存哪裡由伺服器決定。
  • 跟真實環境一樣：公司的檔案系統、雲端硬碟、文件管理系統幾乎都是透過 API 上傳。
  • 可以集中把關：檔名清理、路徑檢查都寫在伺服器一個地方。

防止路徑穿越（Path Traversal）

如果有人把 folder 填成 ../../etc，天真的程式會把檔案寫到伺服器資料夾外面，覆蓋系統檔案。file-server 用兩道防線：

# 第一道：清理每一段名稱
拿掉 / 和 \ 前面的部分、控制字元、Windows 不允許的 < > : " | ? *
丟掉 "." 和 ".."

# 第二道：算出絕對路徑後檢查
full = os.path.abspath(os.path.join(ROOT, rel))
if not full.startswith(ROOT + os.sep):  →  回 403 Forbidden

第一道把明顯的攻擊字串洗掉，第二道不管第一道漏了什麼，最終路徑只要不在 /srv 底下就拒絕。這種「多層防禦」（defense in depth）是資安的基本原則：不要只靠一道檢查。

實測：上傳時 folder 填 ../../etc、filename 填 ../x.pdf，結果檔案被安全地存到 /srv/etc/x.pdf；直接用網址 /..%2f..%2fetc/passwd 讀檔則回 403。

中文檔名的處理

常見的 secure_filename() 函式會把中文全部刪掉（「王小明.pdf」變成「.pdf」），所以這裡自己寫清理規則，只移除危險字元、保留中文。回傳網址時用 urllib.parse.quote 做百分比編碼（〈網路基礎〉），確保網址在任何地方都合法。

n8n：把工作畫成流水線

n8n 是一個工作流程自動化工具。在畫面上把一個個方塊（節點）用線連起來，每個方塊做一件小事，資料就從左流到右。

把它想成工廠流水線：觸發節點是門鈴，門鈴一響，流水線上的工人依序處理同一份資料。有的工人負責查資料，有的負責判斷「要不要繼續」，有的負責送東西出去。

名字 n8n 是 nodemation（node + automation）的縮寫：n 和 n 中間有 8 個字母。

七個核心名詞

名詞意思在我的專案裡
Workflow 工作流一整條流水線流程 1 發送、流程 2 收到回簽通知
Node 節點流水線上的一個工人「下載 PDF」「存到伺服器」「發 Discord 訊息」
Trigger 觸發節點決定流程什麼時候開始追蹤表有列被勾選、計畫書網站送來「已簽署」通知
Item 資料項目節點之間傳的一筆資料（JSON）追蹤表一列＝一位客戶＝一個 item
Expression 運算式用 {{ }} 拿前面的資料{{ $json["客戶名稱"] }} → 王小明
Credential 憑證連外部服務的授權Google 帳號
Execution 執行紀錄每跑一次留下的紀錄失敗時從這裡找是哪個節點出錯

運算式速查

寫法意思結果範例
{{ $json["客戶編號"] }}上一個節點輸出的某個欄位C001
{{ $json.status }}同上，欄位名是英文時可以用點signed
{{ $('取出計畫書ID').item.json["客戶編號"] }}指定某個節點的輸出（不一定是上一個）C001
{{ $json["簽署連結"].split("/s/")[1] }}用 /s/ 切開，取第 2 段P0001-e7ff77
{{ $now.toFormat("yyyy-MM-dd HH:mm") }}現在時間，指定格式2026-11-30 10:12

為什麼要用 $('節點名')？每經過一個節點，$json 就會變成那個節點的輸出。例如「下載 PDF」之後，$json 已經不是追蹤表那一列了。要拿回客戶名稱，就要指名「去『取出計畫書ID』那個節點拿」。所以節點名稱要照指南取，運算式才找得到。

畫面導覽

  • 畫布：中間的大區域，節點拖拉、連線。按節點右邊的 + 接下一個。
  • 節點設定視窗：雙擊節點打開。左邊 INPUT（收到什麼）、中間 Parameters（設定）、右邊 OUTPUT（產出什麼）。
  • Execute step：只跑這個節點，最常用的除錯按鈕。
  • Execute workflow：整條跑一次。
  • 運算式欄位：欄位旁切到 Expression，可以直接把左邊 INPUT 的欄位拖進來，自動產生運算式。

資料模型：items 陣列＋逐項執行

每個節點的輸入輸出都是一個陣列，每個元素是一個 item：

[
  { "json": { "客戶編號": "C001", ... }, "binary": { } },
  { "json": { "客戶編號": "C002", ... }, "binary": { } }
]

大多數節點會對每個 item 各做一次。流程 2 讀到三位「已發送」的客戶，後面的 HTTP Request 就會自動發三次請求，不用自己寫迴圈。json 放一般資料，binary 放檔案（PDF、圖片），兩者分開存放，所以下載 PDF 後要指定「binary 裡的 data 欄位」才能上傳。

$('節點名').item 能找到「同一位客戶在那個節點的資料」，是因為 n8n 會記錄每個 item 從哪個 item 來（paired item）。如果中間節點打亂了對應關係，這個運算式就會報錯，這時改用 .first() 或 .all()。

運算式 {{ }} 裡面其實就是 JavaScript，所以可以用 .split()、.trim()、三元運算子等語法。$now 是 Luxon 函式庫的時間物件，toFormat 用的是 Luxon 的格式代號（MM 月、mm 分，大小寫意思不同）。

憑證存在哪裡

Google 的 OAuth 憑證存在 n8n_data 裡，用一把加密金鑰加密（金鑰在同資料夾的 config 檔）。所以 n8n_data 資料夾等於你的帳號鑰匙，不要上傳到 GitHub 或分享給別人。

為什麼這樣設計

設計理由
Filter 同時要求「已勾選」和「狀態是空的」冪等性（idempotency）：同一件事做兩次結果要跟一次一樣。觸發節點可能因為同一列其他欄位被改而再次送出這列，沒有「狀態是空的」這個條件就會重複傳訊息給客戶
n8n 不直接用追蹤表的網址，而是切出編號再自己組網址追蹤表裡的網址是給客戶用的（localhost），n8n 要走內部網址（plan-site）。另外，只取編號也避免有人在試算表貼一個惡意網址，讓 n8n 去下載不明的東西
先核對客戶編號，再做任何對外動作「先驗證、後動作」：歸檔和傳訊息都是有副作用的動作，必須放在檢查之後
流程 2 收到通知後，仍回頭向 API 查一次不信任外部輸入：通知可能被偽造、重送或內容過時。以資料的「原始來源」（計畫書網站的 API）為準，通知只當作「該去看一下了」的信號
流程 2 核對「狀態必須是已發送」冪等性：同一則通知被重送兩次，第二次狀態已是「已完成」，會走停機分支而不是再歸檔、再回覆一次；也擋掉「沒經過流程 1 就跑來的通知」
讀追蹤表打開 Always Output Data找不到這位客戶時，Get Row(s) 預設會「什麼都不輸出」，流程默默結束、沒人知道。打開後會輸出一筆空資料，讓 If 判斷失敗、走停機通知

Discord Webhook：模擬官方 LINE

Webhook 是一個專屬的投遞口。Discord 給你一個很長的網址，任何程式只要把訊息「投」進這個網址，訊息就會出現在那個頻道。不用建機器人、不用登入。

我幫每位客戶開一個頻道（#王小明、#林美美…），每個頻道一個投遞口，網址寫在追蹤表那位客戶的那一列。這樣 n8n 只要讀那一列，就知道訊息要送去哪裡，不可能送錯頻道。

  1. 建立伺服器Discord 左側 + → 自己建立 → 命名「安心病媒 LINE 模擬」。
  2. 建三個文字頻道#王小明、#林美美、#陳大華。
  3. 建 Webhook頻道名稱旁齒輪 → 整合 → Webhook → 新 Webhook → 名稱改「安心病媒防治」→ 複製 Webhook 網址。
  4. 貼到追蹤表貼到那位客戶的「LINE模擬_DC_Webhook」欄。
  5. 在 n8n 設 HTTP RequestMethod 選 POST，URL 用運算式讀那一欄，Send Body 打開，Body Content Type 選 JSON，內容如下。
傳LINE簽署要求｜JSON Body
{
  "content": "{{ $('取出計畫書ID').item.json['客戶名稱'] }} 您好：\n這裡是安心病媒防治。您預約的「{{ $('取出計畫書ID').item.json['施工類別'] }}」將於 {{ $('取出計畫書ID').item.json['施工日期'] }} {{ $('取出計畫書ID').item.json['施工時間'] }} 到府施工。\n請點以下連結閱讀施工計畫書並完成簽署：\n{{ $('取出計畫書ID').item.json['簽署連結'] }}\n簽署完成後我們會再通知您，謝謝！"
}

客戶在頻道裡看到的樣子：

王小明（假資料） 您好：
這裡是安心病媒防治。您預約的「白蟻防治」將於 2026-12-01 09:00–11:00 到府施工。
請點以下連結閱讀施工計畫書並完成簽署：
http://localhost:8080/s/P0001-e7ff77

\n 是換行。運算式裡的欄位名用單引號 ['客戶名稱']，因為外面的 JSON 字串已經用了雙引號。

  • 回應碼：Discord 成功收到會回 204 No Content（沒有內容要回你）。網址最後加 ?wait=true 會改回 200 和訊息的 JSON，可用來記錄訊息編號。
  • 長度限制：content 最多 2000 字元，制式訊息遠低於此。
  • Webhook 網址就是密碼。網址裡包含一段 token，拿到網址的人就能用公司名義發訊息。所以追蹤表不能公開分享；如果外流，到 Discord 刪掉那個 Webhook 重建即可。

  • 換成真的 LINE：LINE 官方帳號要用 Messaging API 的 push message：POST 到 https://api.line.me/v2/bot/message/push，標頭帶 channel access token，Body 指定客戶的 userId。概念和 Webhook 一樣，只是多了身分驗證，而且免費方案有每月訊息數量限制。

建置步驟：從零開始做一次

總時間約 1.5～2 小時。每一步做完都有「怎麼確認成功」，確認了再往下。

順序是：先把機器開起來（Docker）→ 準備資料（試算表、Discord）→ 最後才畫流程（n8n）。流程要讀試算表、要傳 Discord，所以這些東西要先存在。

A. 啟動容器（約 10 分鐘）

  1. 打開 Docker Desktop等左下角顯示 Engine running。
  2. 開終端機到 Downloads\n8n作業，在檔案總管網址列輸入 cmd 按 Enter。
  3. 如果之前開過，先關掉docker compose down
  4. 啟動docker compose up -d --build，等看到四個容器都是 Started。
  5. 確認瀏覽器打開 localhost:8080（建立施工計畫書）、localhost:8090（公司檔案伺服器）、localhost:5678（n8n）三個都打得開；資料夾裡多了 公司伺服器。

B. Google 試算表（約 10 分鐘）

  1. 新增試算表命名「客戶簽署追蹤表」。
  2. 匯入範本檔案 → 匯入 → 上傳 客戶簽署追蹤表_範本.csv → 取代目前的工作表。
  3. 做勾選框選「開始核可」欄第 2 列以下 → 插入 → 核取方塊；「已回簽」欄也一樣。
  4. 確認伺服器資料夾欄是 C001_王小明 這種名稱；勾選框點得動。

C. Discord（約 10 分鐘）

  1. 建伺服器和三個客戶頻道見〈Discord Webhook〉。另外建一個 #系統通知 給停機訊息用，也建一個 Webhook。
  2. 把 Webhook 網址貼進試算表每位客戶那一列。
  3. 確認網址都以 https://discord.com/api/webhooks/ 開頭。

D. 建一份測試計畫書（約 3 分鐘）

  1. localhost:8080 建立 C001 的計畫書客戶編號一定要填 C001，跟試算表一致。
  2. 複製簽署連結貼到試算表 C001 那一列先不要勾選、不要簽名。

E. n8n（約 60 分鐘）

  1. 第一次打開建立擁有者帳號帳號只存在你電腦的 n8n_data。
  2. 建立憑證左側 Credentials → Add：① Google Sheets OAuth2 API，照課程 13.1 完成授權；② Header Auth，Name 填 X-Webhook-Secret，Value 填 anxin-demo-secret-2026（和 docker-compose.yml 一樣）。
  3. 建流程 1Create Workflow → 命名「流程1_發送」→ 照〈流程逐節點〉互動拆解的「流程 1」逐一加節點、照抄設定與名稱。
  4. 一節點一測試每加一個就按 Execute step，看 OUTPUT 跟〈流程逐節點〉的示意一不一樣，一樣再加下一個。
  5. 整條測試到試算表勾 C001 的開始核可 → 回 n8n 按 Execute workflow，或等觸發節點。
  6. 確認localhost:8090 出現 C001_王小明/C001_未簽署.pdf；#王小明 收到簽署要求；試算表狀態變「已發送」。
  7. 建流程 2 的第一個節點命名「流程2_收到回簽」，加 Webhook 節點（POST、Path plan-signed、Header Auth、Respond Immediately）。
  8. 抓一筆真實通知在 Webhook 節點按 Listen for test event → 點 Discord 裡的連結簽名送出。n8n 會立刻收到資料（網站發現正式網址還沒啟用，自動改送測試網址）。
  9. 往下接節點照〈流程逐節點〉「流程 2」。要再測時：再按一次 Listen，然後到 localhost:8080 清單按那份計畫書的「重送」，不用重新簽。
  10. 確認幾秒內：出現 C001_已簽署.pdf、已回簽打勾、狀態「已完成」、#王小明 收到「已收到您的簽署」；8080 清單顯示「已通知」。
  11. 啟用兩條流程右上角 Active／Publish 打開，之後不用開著 n8n 畫面也會自動跑。再建一份新計畫書從頭跑一次，8080 清單應顯示「已通知・正式網址」。

增量開發：一次只加一個節點、立刻測試，是除錯成本最低的做法。一口氣接完九個節點才測，出錯時要同時懷疑九個地方。

測試資料隔離：正式錄影前，可以把 plan_data 和公司伺服器資料夾清空，再從 P0001 開始重做一次，畫面比較乾淨。清空前先 docker compose down，避免檔案正被使用。

Pin data：n8n 可以把某個節點的輸出「釘住」（Pin），之後測試後面的節點時不用每次重新觸發前面的流程，在調整 Discord 訊息格式時特別省時間。記得正式啟用前取消釘選。

二分法定位

流程有九個節點時，不要從第一個慢慢看。先看中間（第 5 個）的 INPUT 對不對：對，問題在後半；不對，問題在前半。每次排除一半，最多看 4 次就能定位。這就是二分搜尋用在除錯上。

用 curl 繞過 n8n 測試

懷疑是網站還是 n8n 的問題時，直接在終端機發請求，排除 n8n：

# 查計畫書（在 Windows 上，所以用 localhost）
curl http://localhost:8080/api/plans/P0001-e7ff77

# 模擬 n8n 上傳
curl -F "file=@test.pdf" -F "folder=C001_王小明" -F "filename=test.pdf" http://localhost:8090/api/upload

# 手動重送「已簽署」通知給 n8n，回傳結果
curl -X POST http://localhost:8080/api/plans/P0001-e7ff77/notify

# 從 n8n 容器裡面測（驗證內部網址）
docker exec -it n8n wget -qO- http://plan-site:8080/api/plans/P0001-e7ff77

curl 成功、n8n 失敗 → 問題在 n8n 節點設定；curl 也失敗 → 問題在網站或網路。

上線考量：變成正式系統還差什麼

把這個雛型變成公司真正能用的系統，技術上還需要處理以下事項（目前的限制整理在專案介紹的〈限制與未來〉）。

上線檢查清單

  • HTTPS：簽署頁傳輸姓名、地址、簽名圖檔，必須加密。常見做法是在前面放反向代理（Nginx、Caddy）自動申請憑證。
  • 電子簽章的法律效力：台灣有《電子簽章法》，要讓電子簽名在爭議時站得住，通常需要確認簽署人身分、保存簽署時間與 IP、讓文件簽後無法被竄改（例如對 PDF 做數位簽章或存雜湊值）。這部分應該交給專業的電子簽署服務或公司法務評估。
  • 機密管理：Webhook 網址、LINE token、Google 憑證不能寫死在流程裡或放在共用試算表，要放在 n8n Credentials 或環境變數。
  • 權限最小化：n8n 的 Google 帳號只授權這一份試算表需要的範圍；檔案伺服器的上傳 API 要加 API key，避免任何人都能往裡面丟檔案。
  • 備份：n8n_data（流程與憑證）、plan_data（計畫書與簽名）、公司伺服器（PDF）三個資料夾定期備份。
  • 版本固定：image 從 latest 改成固定版本號，升級前先在測試環境試過。
  • 監控：Error Workflow 通知、定期檢查「已發送超過 3 天未簽」的客戶並提醒承辦。
  • Webhook 簽章：正式系統常用 HMAC 簽章取代固定密語：發送端用金鑰對「內容＋時間戳」算出簽章放在標頭，接收端重算比對，並拒絕太舊的時間戳。這樣就算有人截到一則通知，也無法竄改內容或拿去重播。
